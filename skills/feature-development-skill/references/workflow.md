## 1. Operating modes

### Initialize

Use when a qualifying feature has no durable workspace. Inspect repository conventions first, then create the minimum structure. Do not pre-fill speculative technical conclusions.

### Discover

Use when the current architecture, data flow, or scope is not yet sufficiently understood for an implementation plan. Capture confirmed facts, assumptions, risks, and open questions. Discovery may end with a staged roadmap, but it does not imply approval to implement.

### Plan

Create one stage plan that is implementable and reviewable. The plan should be specific where failure would be costly and flexible where multiple safe implementations are valid.

### Implement

Execute only an approved stage. The implementation report is an evidence index, not a narrative rewrite of the plan.

### Review

Independently inspect implementation. A report generated by the same agent that wrote the code is useful evidence but is not independent verification.

### Close stage

Move durable outcomes into the roadmap, preserve detailed history in stage files, update deferred requirements, and rewrite the handoff.

### Resume

Reconstruct state from repository evidence. Never infer completion from checked boxes alone.

## 2. Lifecycle transitions

Recommended transitions:

```text
Backlog → Discovery → Planned → In progress
In progress → Implemented — unverified
Implemented — unverified → Needs changes → In progress
Implemented — unverified → Verified
Needs changes → Implemented — unverified
Any non-terminal state → Blocked
Blocked → prior valid state
Backlog/Planned → Deferred
Backlog/Planned → Cancelled
```

Do not transition directly from `Planned` to `Verified`.

A stage can have partially verified scope. Record it explicitly rather than forcing a false binary status.

## 3. File-update matrix

| Mode | ROADMAP | HANDOFF | PLAN | IMPLEMENTATION | REVIEW |
|---|---|---|---|---|---|
| Initialize | Create | Create | Optional | No | No |
| Discover | Update facts/stages | Update | Draft if ready | No | No |
| Plan | Update proposed/approved status | Update next action | Create/revise before approval | No | No |
| Implement | Set In progress/result links | Update | Read only after approval | Create/update | No |
| Review | Update status only when justified | Update | Read only | Read/correct factual errors | Create/update |
| Close stage | Record verified result and deferred IDs | Rewrite | Frozen | Final factual corrections only | Final disposition |
| Resume | Correct stale state only with evidence | Rewrite if stale | Read active | Read active | Read active |

## 4. Approval and verification boundaries

### Plan approval

Only explicit user approval, an approved PR/issue state defined by the repository, or another clearly delegated authority may mark a plan approved. An agent cannot infer approval from silence.

### Implementation completion

`Implemented — unverified` means the code and report exist and reported checks ran. It does not mean the implementation is correct or deployed.

### Verification

Verification requires inspection of the implementation and relevant evidence. The reviewer should identify what was not inspected. If a controlled production check is part of the stage's completion criteria, keep that gap visible until completed.

## 5. Context handoff

Keep `HANDOFF.md` short enough to read at the beginning of a new session. Target fewer than 150 lines and never exceed 200 lines without a clear project-specific reason.

Include:

- feature and active stage;
- current evidence status;
- last verified outcome;
- confirmed decisions that constrain the next step;
- unresolved blockers;
- deferred IDs due in the active stage;
- source documents to read;
- exact next action.

Do not include full plans, diffs, review transcripts, or historical discussion. Link to them.

## 6. Recovery from drift

When documents and code disagree:

1. inspect the repository and version history;
2. identify the last evidence-backed state;
3. mark uncertain claims as requiring verification;
4. correct roadmap and handoff with an explicit note;
5. do not rewrite stage history to hide the drift;
6. create a repair plan if the discrepancy affects correctness.
